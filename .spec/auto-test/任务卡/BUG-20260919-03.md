# BUG-20260919-03【P1】live 阶段无数据新鲜度看门狗：真实断流不显示失败横幅，服务恢复后页面永不自动恢复

| 字段 | 内容 |
|---|---|
| 级别 | P1（功能错误 + 验收闭环缺失；TV 挂屏核心场景静默冻结且健康状态误导） |
| 类型 | 功能 |
| 位置 | `apps/dashboard/src/features/realtime/hooks/useRealtimeStream.ts`（live 阶段后续航逻辑） |
| 关联用例 | TC-RT-E2E-07 / TC-RT-E2E-08（AC-M02-007） |
| 发现轮次 | run-20260919-R1 |

## 现象
实时大屏正常显示后杀掉数据服务进程：页面**持续显示「正常更新中」徽标**、不出现「更新失败」横幅与最后成功时点（观察 2 分钟无变化）；随后重启数据服务，页面**仍冻结在断流时刻的数据，永不自动恢复**（再观察 2 分钟无变化），仅手动刷新才恢复。单测 AC-007（模拟 EventSource error）通过，但真实浏览器断流不触发同一路径。

## 复现步骤（可直接照做）
1. `node apps/server/mock-realtime-server.mjs`（8787）+ `pnpm --filter @web-monitor/dashboard dev`（5180），打开 http://127.0.0.1:5180/realtime，确认「正常更新中」
2. `taskkill /F` 杀掉 mock 进程（本次实测 08:37:06）
3. 静置 ≥2 分钟，观察徽标与横幅 → 实测始终「正常更新中」、无横幅
4. 重启 mock（新进程监听 8787），静置 ≥2 分钟 → 实测统计时点冻结在断流前值（00:37），不恢复

## 期望 vs 实际
- 期望：断流后进入「更新中断」态（横幅 + 最后成功时点，AC-M02-007 / FTDD 状态机 interrupted）；服务恢复后自动回到 live 并继续推进。契约 `packages/types/src/realtime.ts` RealtimeFailure 注释明确「**连接中断由客户端超时判定**」
- 实际：徽标恒为「正常更新中」、数据冻结，恢复后亦不自愈

## 证据
- 截图：`evidence/screenshots/realtime_TC07_断流2分钟状态.png`（断流 2 分钟后仍「正常更新中」+ 冻结数据）
- 轮询时间线：08:37:15→08:39:06 每 4s 采样 12 次 badge=正常更新中；恢复后 08:39:53→08:40:49 采样 12 次 point=00:37 恒定（见任务卡附注 / 报告 R1 轮记录）
- console：全程 0 error（无报错，属静默失效）
- 定位线索（方向，不下结论）：hook 在收到首帧后仅依赖 EventSource `error` 事件进入 interrupted（`useRealtimeStream.ts` error 监听）；经 vite 代理的 SSE 在 upstream 进程死亡后客户端连接呈半开、无任何事件到达浏览器 → live 阶段缺「帧新鲜度超时」兜底；现有 `startFallbackPolling` 已具备恢复后自愈能力，但看门狗缺失导致它永远不被启动
