# BUG-20260919-04【P1】REST 快照兜底请求双前缀 404：断流后被误判「应用不可用」并停摆自愈轮询

| 字段 | 内容 |
|---|---|
| 级别 | P1（功能错误：断流恢复链路死锁 + 误导性「应用被删」提示） |
| 类型 | 功能 |
| 位置 | `apps/dashboard/src/features/realtime/api.ts`（`fetchSnapshot`/`snapshotUrl` 与 axios baseURL 拼接） |
| 关联用例 | TC-RT-E2E-08（AC-M02-007 恢复路径） |
| 发现轮次 | run-20260919-R2（BUG-03 修复后回归暴露） |

## 现象
真实断流→恢复复测中：断流后正确出现「更新失败」横幅（BUG-03 修复生效），但随后页面误显示「**该应用不可用（可能已被删除）**」，且服务恢复后页面**永不自愈**（该提示 + 数据统计时点「—」持续不动）。同时页面顶部出现内容为「ok」的红色错误 toast。

## 根因（已实测实锤）
- `apps/dashboard/src/api/client.ts` 的 axios 实例 `baseURL: '/api/v1'`；
- `realtime/api.ts` 的 `snapshotUrl` 自带 `/api/v1` 前缀，`fetchSnapshot` 以 `get(snapshotUrl(...))` 调用 → axios 拼接为 **`/api/v1/api/v1/realtime/screen/:appKey/snapshot`**（双前缀）；
- 该双前缀 URL 经 vite 代理到数据服务后命中不了任何路由，数据服务返回 **HTTP 404**（实测：`curl http://127.0.0.1:5180/api/v1/api/v1/realtime/screen/wm_demo00000001/snapshot` → 404；单前缀同路径 → 200）；
- 兜底轮询 catch 到 404 → `isAppNotFound` 判 true → 置 `appNotFound` 并清空全部计时器 → 轮询停摆；此时 EventSource 已因断流期间的代理 500 进入致命关闭不再重连 → 页面死锁；
- 顶「ok」toast：axios 错误拦截器展示 `error.response.data.message`，而数据服务 404 响应体为 `{code:0,message:'ok'}`；
- **为何此前未暴露**：SSE 走原生 EventSource（单前缀路径正常），快照兜底轮询在 BUG-03 修复前从不启动，双前缀请求从未真正发出过。

## 复现步骤（可直接照做）
1. mock(8787) + vite(5180) 在线，打开 /realtime 确认「正常更新中」
2. 杀 mock 进程 → ≤15s 出现「更新失败」（正确）→ 再等 ≤15s 出现「该应用不可用（可能已被删除）」（错误）+ 顶部「ok」红 toast
3. 重启 mock → 静置任意时长，页面不自愈
4. 实证：`curl http://127.0.0.1:5180/api/v1/api/v1/realtime/screen/wm_demo00000001/snapshot` → HTTP 404；`curl http://127.0.0.1:5180/api/v1/realtime/screen/wm_demo00000001/snapshot` → HTTP 200

## 期望 vs 实际
- 期望：兜底轮询请求命中 `/api/v1/realtime/screen/:appKey/snapshot`（TDD 契约路径，L1 直连已验证 200）；断流恢复后自动回 live；`isAppNotFound` 仅在真实 404（应用被删）时触发
- 实际：兜底请求双前缀 404 → 误判 + 死锁
