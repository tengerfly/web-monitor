# web-monitor 架构设计

## 1. 总体架构

```
                     ┌───────────────────────── 接入方业务系统 ─────────────────────────┐
                     │  原生 Web  │  React 应用  │  Vue 应用  │  （未来）小程序 / Node │
                     └──────┬──────────┬──────────────┬───────────────────────────────┘
                            │          │              │
                     ┌──────┴──────────┴──────────────┴───────┐
                     │        @web-monitor/core（底座）         │
                     │  配置中心 · 会话 · 上下文 · 事件总线      │
                     │  上报管道 · 本地队列 · 采样 · Hooks       │
                     └───┬──────────┬──────────┬────────┬──────┘
                         │          │          │        │
              ┌──────────┴──┐ ┌─────┴─────┐ ┌──┴─────┐ ┌┴──────────┐
              │ performance │ │ behavior  │ │ error  │ │  replay   │
              │  性能监控   │ │ 行为追踪  │ │错误溯源│ │ 会话回放  │
              └─────────────┘ └───────────┘ └────────┘ └───────────┘
```

## 2. 包依赖关系

```
@web-monitor/types        （零依赖，纯类型 + 常量 + 枚举）
      ▲
      │
@web-monitor/core         （底座，唯一必装包）
      ▲
      ├── @web-monitor/performance
      ├── @web-monitor/behavior
      ├── @web-monitor/error ──► @web-monitor/replay（可选，用于错误现场关联）
      ├── @web-monitor/replay
      ├── @web-monitor/react  （依赖 core，对等依赖 react）
      └── @web-monitor/vue    （依赖 core，对等依赖 vue）
```

**约束**：
- 能力包之间**不互相依赖**（`performance` 不 import `behavior`），保证按需引入时的树摇干净。
- 能力包只依赖 `core` 暴露的公共 API（`MonitorContext`、`emitter`、`hooks`、`transport.push`）。
- `error` 对 `replay` 的依赖通过**事件总线解耦**，而非硬引用：`error` 发布错误时刻，`replay` 若存在则打标记。

## 3. 运行时数据流

### 3.1 采集 → 上报
```
浏览器 API / 业务调用
   │  (PerformanceObserver / addEventListener / 拦截器 / track())
   ▼
Collector 采集器     ← plugins 注册，各自独立 enable/disable
   │  emit(event)
   ▼
MonitorContext       ← 注入 base 字段（appKey/sessionId/userId/context/traceId）
   │  hooks.beforePush
   ▼
EventBus             ← 内部广播（供 breadcrumb、replay 标记消费）
   │  hooks.beforeSend
   ▼
Transport            ← 采样 → 入队 → 批量 → 定时/满额/隐藏时 flush
   │
   ├─ navigator.sendBeacon()   （页面卸载场景首选）
   ├─ fetch(keepalive)         （保底）
   └─ Image 打点               （极端降级）
   ▼
失败 → LocalQueue（localStorage，带 TTL 与容量上限）→ 下次启动补报
```

### 3.2 溯源数据流
```
错误发生
   ├─ 取 BreadcrumbBuffer 最近 N 条（点击/路由/请求/输入/console）
   ├─ 取 ErrorSnapshot（内存/网络/可见性/路由/最近请求结果）
   ├─ 计算 fingerprint（name + 归一化 message + 堆栈特征）
   ├─ 生成 traceId（若能关联到失败的请求，复用其 traceId）
   ▼
error 事件（含 breadcrumbs + snapshot + fingerprint）
   │
   ▼
服务端：按 fingerprint upsert ErrorGroup → 关联 Session / UserId → 触发告警规则
   │
   ▼
看板：错误详情页 ← 同 sessionId 拉取 behavior 时间线与 replay 分片
```

## 4. 存储设计

### 4.1 PostgreSQL（实体、聚合、配置）
| 表 | 用途 |
|---|---|
| `projects` | 应用（appKey、名称、采样率、开关、脱敏规则、保留天数） |
| `error_groups` | 错误分组（fingerprint、首末次出现、次数、影响用户/会话数、状态、指派） |
| `sourcemaps` | SourceMap 文件（应用、版本、文件名、内容、更新时间） |
| `alert_rules` | 告警规则（指标、阈值、窗口、静默期、渠道） |
| `alert_records` | 告警触发记录与状态 |
| `members` | 成员与角色（多租户预留） |

### 4.2 ClickHouse（海量明细与聚合）
| 表 | 用途 | 分区 / TTL |
|---|---|---|
| `wm_events` | 统一事件明细（性能指标、行为事件、自定义埋点） | 按月分区，TTL 90 天 |
| `wm_errors` | 错误明细（含 breadcrumbs / snapshot JSON） | 按月分区，TTL 90 天 |
| `wm_sessions` | 会话（ReplacingMergeTree，随会话推进更新） | 按月分区，TTL 180 天 |
| `wm_replay` | 回放分片（sessionId + chunkIndex） | 按月分区，TTL 30 天 |

**为什么双库**：PG 擅长事务与关系（错误分组状态流转、告警规则、权限）；CH 擅长海量写入与列式聚合（PV/UV、趋势、P95、明细检索）。查询按语义路由，不做跨库 JOIN（用 `appKey + sessionId` 在应用层拼装）。

## 5. 上报协议要点（详见 `03-上报协议.md`）

- **单一入口**：`POST /api/v1/ingest`，body 为 `{ appKey, sdk, events: [] }`。
- **公共字段 + 载荷分离**：所有事件共享 `BaseEvent`（会话、用户、上下文、traceId），差异部分放 `payload`。
- **可扩展**：新增采集能力只需新增 `type/category` 与 payload 结构，服务端按 `category` 分发，无需改协议版本。
- **前向兼容**：服务端白名单之外的字段丢弃但不报错；客户端对未知响应字段忽略。

## 6. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 性能与行为是否合并 | **物理分离为两个包** | 用户明确要求按需使用；两者数据模型与消费场景完全不同，合并会导致体积不可控 |
| 请求拦截归属 | 放在 `core` | 性能需要耗时、错误需要失败原因，两份代码重复拦截会互相覆盖 |
| 错误指纹在哪算 | 前端预计算 + 服务端复核 | 前端算可保证同一构建产物的确定性；服务端复核防止伪造与归一化差异 |
| 回放数据结构 | **对齐 rrweb 的 type/source** | 自研录制器轻量可控，同时保留切换社区播放器/生态的能力 |
| 循环缓冲区 | 定长环形数组 | breadcrumbs 高频写入，避免数组 shift 的 O(n) 开销 |
| 双存储 | PG + CH | 事务与聚合各取所长；CH 承担亿级明细写入 |
| 服务端写入路径 | 请求内只入队，后台批量写 | 网关必须极轻，避免被存储抖动拖垮 |
| SDK 打包 | Rollup，ESM/CJS/UMD 三形态 | 兼容现代打包器、Node 侧引用与 `<script>` 直引三种接入方式 |

## 7. 部署形态

```
docker compose up -d
├── postgres:16
├── clickhouse:24
└── （可选）mailhog 用于本地验证邮件告警

pnpm db:migrate && pnpm db:ch   # 初始化库表
pnpm dev:server                 # 网关 127.0.0.1:8787
pnpm dev:dashboard              # 看板 127.0.0.1:5180
```

生产建议：网关多实例 + 前置 Nginx/网关限流；CH 单机起步、按分区扩容；看板静态托管。
